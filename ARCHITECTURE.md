# Arquitetura do Boom, listener!

Documento de referência da estrutura do app. O `CLAUDE.md` resume as regras; aqui fica o porquê de cada peça.

## Visão geral

App Android nativo em **Kotlin + Jetpack Compose (Material 3)**, dividido em **módulos Gradle**. Cada módulo tem uma responsabilidade só, compila separado e só enxerga o que declarou como dependência, então um bug fica "preso" no módulo onde nasceu e uma atualização mexe em poucos lugares.

Princípios herdados do BusBus:
- **Local e privado por padrão:** sem conta, sem anúncio, nada sai do aparelho além das consultas de informação pública (tabela abaixo) e da verificação de versão nova no GitHub. Detalhes em [`docs/privacy.md`](docs/privacy.md).
- **Fonte única da verdade:** versão, dependências e regras de build em um lugar só.
- **Build automático, release com aprovação:** cada push na `main` gera o APK assinado como artefato para vistoria; a Release do GitHub só sai por tag, depois da aprovação do mantenedor.

## Mapa dos módulos

```
app/                      ← ponto de entrada: Activity, navegação, injeção de dependências
build-logic/              ← plugins de convenção do Gradle (config compartilhada)
gradle/libs.versions.toml ← catálogo de versões (única lista de dependências)

core/
  model/          ← classes de dados puras (Track, Album, Artist, Release…). Sem nenhum import android.*
  common/         ← utilidades: Result, dispatchers, log, formatação de tempo
  designsystem/   ← tema M3, cor dinâmica, cor extraída da capa, componentes visuais reutilizáveis
  datastore/      ← preferências do usuário (DataStore)
  player/         ← Media3 (ExoPlayer) + MediaSessionService: fila, notificação, tela de bloqueio, Bluetooth

data/
  library/        ← lê o MediaStore (com o filtro de pastas e duração), expõe faixas, álbuns, artistas e playlists
  tags/           ← lê e grava tags nos arquivos (TagLib nativo) + pedido de permissão de escrita
  deezer/         ← API do Deezer: foto do artista, discografia, lançamentos, faixas
  lastfm/         ← API do Last.fm (via proxy): biografia, tags de gênero, similares, scrobble
  musicbrainz/    ← reserva quando o Deezer não acha: MusicBrainz (tags, discografia) + capas do Cover Art Archive
  releases/       ← artistas seguidos, comparação de discografia, WorkManager diário, notificações
  wellbeing/      ← estatísticas de escuta (mais ouvidas) e, depois, tempo de escuta e avisos de tela
  profile/        ← seu perfil, só seu e só no aparelho: nome, descrição, cor, foto e capa (recorte e GIF animado)
  lyrics/         ← letras: LRCLIB + cache no aparelho + leitor de LRC
  updates/        ← "Verificar atualizações": compara a versão instalada com a última Release do GitHub

feature/
  library/        ← telas da biblioteca: músicas, álbuns, artistas, pastas, busca
  nowplaying/     ← player em tela cheia + mini player
  artist/         ← página do artista: foto, bio, discografia com "tenho / falta"
  tageditor/      ← edição de tags de uma ou várias faixas
  releases/       ← lançamentos (abre pelo sino no topo das abas) e gerenciamento de quem você segue
  settings/       ← ajustes, tema, sobre, licenças, privacidade
  wellbeing/      ← estatísticas de escuta e configuração dos avisos
  profile/        ← aba Perfil: o seu perfil personalizado, com estatísticas, mais ouvidas, artistas e histórico

proxy/            ← Cloudflare Worker que guarda a chave e o segredo do Last.fm (igual ao do BusBus)
```

## Regra de dependências

```
app ──► feature/* ──► data/* ──► core/*
```

- **`feature` nunca depende de outra `feature`.** A navegação entre telas é feita pelo `app`, que conhece todas. Isso permite apagar ou reescrever uma tela sem quebrar as outras.
- **`data` nunca depende de `feature`.** Cada módulo `data` expõe uma interface `…Repository`; a implementação fica `internal`.
- **`core` não depende de `data` nem de `feature`.** `core/model` não depende de nada.
- `feature` pode usar `core/designsystem`, `core/model` e `core/common` diretamente.

Se uma mudança "precisa" quebrar essas setas, o código está no módulo errado.

## Dentro de um módulo `feature`

Padrão MVVM com estado único por tela:

```
feature/artist/
  ArtistScreen.kt       ← Composable: só desenha o estado e repassa eventos
  ArtistViewModel.kt    ← junta os repositórios, expõe StateFlow<ArtistUiState>
  ArtistUiState.kt      ← sealed interface: Loading / Success / Error
  ArtistNavigation.kt   ← rota e função de navegação que o `app` registra
```

A tela nunca chama repositório nem API direto; tudo passa pelo ViewModel.

## Fontes de dados externas

| Fonte | Uso | Chave | Observação |
|---|---|---|---|
| MediaStore | arquivos de música do aparelho | — | fonte da biblioteca |
| Deezer API | foto do artista, discografia, lançamentos | não precisa | ~50 req / 5 s por IP; respostas em cache |
| MusicBrainz + Cover Art Archive | reserva do Deezer: tags, capa, discografia | não precisa | 1 consulta/s e User-Agent do app; cache de 7 dias |
| Last.fm API | biografia e gênero | sim | chamado **só via `proxy/`** (Cloudflare Worker), a chave nunca vai no APK |
| LRCLIB | letras (sincronizadas quando houver) | não precisa | só quando a pessoa abre a letra |
| GitHub API | versão nova e foto do desenvolvedor | não precisa | `ETag` (304 não gasta o limite) |

O que vem de fora fica em cache em arquivo (JSON e imagens, no `cacheDir` de cada módulo `data`), para não repetir consultas. Não existe banco Room: os dados do usuário ficam em DataStore e arquivos.

## Fluxos principais

- **Biblioteca:** `data/library` escuta mudanças do MediaStore → sobe `version` → as telas recarregam.
- **Edição de tags:** `feature/tageditor` → `data/tags` pede permissão de escrita (Android 11+ usa `MediaStore.createWriteRequest`) → grava → pede reescaneamento do arquivo → `LibraryRepository.notifyChanged` (lista e capas recarregam) e `PlaybackController.updateTrackInfo` (fila e notificação sem parar a música).
- **Tags automáticas:** o ViewModel do editor junta `data/deezer` (`searchTrack` + `rankCandidates`, testado com acentos, "feat." e homônimos; depois `trackTags` com faixa, disco, ano, capa) e `data/lastfm` (`trackTags` + `pickGenre`, gênero mais preciso). Resultado claro (≥ 0,8 e 0,1 à frente do segundo) preenche sozinho; senão o usuário escolhe. Nada é gravado sem tocar em Salvar. Se o Deezer não achar (ou estiver fora do ar), a busca vai ao `data/musicbrainz` com as mesmas regras de comparação (`rankCandidates`), e a capa vem do Cover Art Archive.
- **Página do artista:** Deezer e Last.fm (com cache em arquivo); MusicBrainz quando o Deezer não acha.
- **Radar de lançamentos:** `data/releases` associa os artistas locais a IDs do Deezer; um WorkManager (a cada ~12 h, com internet) compara a discografia com a última checagem e notifica o que é novo.
- **Avisos de tela:** `data/wellbeing` soma o tempo de reprodução vindo do `core/player`; ao passar do limite configurado, mostra um aviso leve (nunca bloqueia).

## Design

Base: **Material 3 Expressive**, a evolução do M3 lançada com o Android 16. Ela traz paletas mais ricas, fontes variáveis, formas que se transformam ("shape morphing") e movimento com física de mola.

**Versão da biblioteca:** `androidx.compose.material3` **1.5.0** (em beta desde outubro de 2026). A 1.4.0 estável ainda não tem a maior parte dos componentes Expressive. Quando a 1.5.0 sair estável, troca-se só a versão no catálogo.

**Tema (`core/designsystem`)**
- **Cor:** 5 cores-chave, cada uma gerando uma paleta de 13 tons. Usamos papéis (`primary`, `secondary`, `tertiary`, `surface…`), nunca hex. Cor dinâmica no Android 12+, com tema próprio como fallback. No player, o esquema é gerado a partir da cor dominante da capa (com Palette ou MaterialKolor).
- **Tipografia:** a escala M3 de 15 estilos (display, headline, title, body, label × large/medium/small). Fonte variável (Roboto Flex ou outra) para usar peso e largura como efeito, por exemplo no título da música que está tocando.
- **Forma:** os 5 tamanhos (extraSmall a extraLarge) e as `MaterialShapes` do Expressive para capas, botões e indicadores.
- **Movimento:** `MaterialTheme.motionScheme` (molas "expressive" ou "standard"), nunca durações escritas à mão.
- **Elevação:** tonal (camadas de cor de superfície), sombra só onde precisa destacar algo.

**Componentes previstos**

| Onde | Componente M3 |
|---|---|
| Navegação principal (≤ 5 abas) | `NavigationBar` em qualquer tela (sem layout próprio de tela larga) |
| Barra de progresso da música | `Slider` com trilha ondulada / `LinearWavyProgressIndicator` (o mesmo estilo do player do Android 16) |
| Controles do player | `ButtonGroup` com botões que mudam de forma ao tocar |
| Carregando | `LoadingIndicator` (formas que se transformam) |
| Busca na biblioteca | `SearchBar` (slot-based, estável desde 1.5.0-alpha24) |
| Ações na lista ou seleção | `FloatingToolbar` / `FlexibleBottomAppBar` |
| Álbuns e lançamentos em destaque | `Carousel` |
| Listas de faixas | List items Expressive (agrupados, com cantos que se adaptam) |

## Stack

- Kotlin 2.4, Jetpack Compose e Material 3 (Expressive), com cor dinâmica.
- Media3: ExoPlayer + MediaSession (tocar), Transformer + Effect (vídeo do "Compartilhar banner").
- DataStore e SharedPreferences para ajustes; arquivos JSON (org.json) para os dados da pessoa. Sem Room.
- WorkManager (radar de lançamentos), Palette (cor da capa), Navigation Compose.
- TagLib para Android (`io.github.kyant0:taglib`): tags de MP3, FLAC, M4A, OGG, OPUS, WAV… Trabalha com o descritor de arquivo do MediaStore, o único jeito de gravar no Android 10+.
- Reorderable (`sh.calvin.reorderable`) para arrastar na fila e nas playlists.
- Rede com `HttpURLConnection` puro (sem OkHttp/Retrofit) e imagens com cache próprio (sem Coil).
- Sem injeção de dependências por enquanto: cada `data` expõe um ponto de acesso (`LibraryData.repository(context)`, etc.) que devolve sempre a mesma instância.
- Testes: JUnit, kotlinx-coroutines-test e org.json de verdade nos testes de unidade.

## Build e release

- Versão definida **só** em `gradle.properties` (`APP_VERSION=X.Y.Z`); o `versionCode` é calculado como `MAJOR*10000 + MINOR*100 + PATCH`. A versão só sobe no release (ver CLAUDE.md).
- `.github/workflows/ci.yml`: todo push na `main` roda `testDebugUnitTest assembleRelease` (R8 + assinatura) e guarda `boomlistener_v{versão}.apk` como artefato ("build para vistoria"). Uma tag `vX.Y.Z` confere `APP_VERSION` e a seção do CHANGELOG e publica a Release com essa nota. Se o build falha, a Action posta o resumo do erro como comentário no commit.
- Assinatura: a Action decodifica a keystore dos Secrets e passa o caminho em `ANDROID_KEYSTORE_PATH` (mais senha e alias); o `app/build.gradle.kts` assina o release só quando a variável existe.
- JDK 21 e o SDK que já vem no runner `ubuntu-latest` (sem `setup-android`), lições já aprendidas no BusBus.

# Comportamentos em detalhe

O que cada parte faz e por quê, com os nomes do código. O `CLAUDE.md` traz só as regras; os detalhes ficam aqui.

## Modo offline

- `OfflineMode` (core/common, SharedPreferences, desligado por padrão; ligado em Ajustes) é lido no `BoomApplication`. Ligado, **todo** `openConnection` dos repositórios (Deezer, Last.fm, MusicBrainz, LRCLIB, imagens) chama `OfflineMode.requireOnline()` antes e falha como falta de internet; o `ReleaseCheckWorker` não consulta nada. Só a verificação de atualizações (`data/updates`) continua. O que já está em cache continua aparecendo. Código novo que abra conexão **tem** que chamar `requireOnline()` antes.

## Player

- A reprodução mora em `core/player`: `PlaybackService` (Media3 `MediaSessionService` + ExoPlayer) toca de verdade; as telas falam só com a interface `PlaybackController` (`PlayerConnection.controller(context)`).
- Notificação, tela de bloqueio, fone Bluetooth e Android Auto vêm de graça do `MediaSession`; não crie notificação de mídia à mão.
- Desde o Media3 1.11, o `MediaSession` exige ser usado na thread principal. O controller já posta tudo no `Looper` principal; mantenha assim.
- O player em tela cheia **não é uma tela da navegação**: é um painel (`PlayerSheet`) por cima do app inteiro, controlado por `PlayerSheetState` (0 = fechado, 1 = aberto). O mini player abre (toque ou puxar para cima) e encerra a música (puxar para baixo). O "voltar" do sistema fecha o painel com voltar preditivo. Saindo do player aberto para outra tela (artista, editor de tags), o `:app` guarda a tela de origem (`reopenPlayerOn`) e reabre o player ao voltar até ela. O player **cresce a partir do mini player**: o `:app` marca o mini player com `playerSheetAnchor` (topo e base dele em `collapsedTopPx`/`collapsedBottomPx`); o `PlayerSheet` desenha um cartão (`InsetRoundedShape`) que começa com as margens e cantos do mini player e cresce até a tela toda (o dedo segue `travelPx`), a barra de abas desce junto (`PlayerSheetState.fraction`), uma cópia do `MiniPlayer` esmaece no começo (até 30%) e a tela cheia aparece depois (de 20% a 65%). Mini player, cartão e player aberto usam a mesma cor: `rememberPlayerTint` (capa pequena) → `artworkTopTint` (core/designsystem), que é o fundo do `BoomArtworkSurface` e o topo do `artworkTintedBackground`. Em volta do mini player, uma luz fraca no tom da capa (`dropShadow` no `BoomArtworkSurface`), para não se misturar com a página. O `QueuePager` fica dentro de `key(ordem da fila)`: mudar a ordem (aleatório) cria um carrossel novo já na música atual, sem correr pelas capas. Capas do player ficam numa memória (`ArtworkMemory`, ~24 MB) para não piscar a inicial quando o carrossel remonta a página. O mini player **flutua por cima das telas**, sem faixa de fundo atrás dele: no `:app` ele fica num `Box` sobre o `navGraph`, mede a própria altura e a passa como `LocalBottomOverlay` (core/designsystem); o `BoomScreenScaffold` soma isso ao `padding` de baixo e ao `snackbarHost` (avisos ficam acima do mini player), e listas fora dele (artista, álbum, perfil) somam `LocalBottomOverlay.current` no `contentPadding`. A fila (`QueuePanel`) tem fundo escurecido que segura os toques no player (tocar nele fecha a fila), lista sem `overscrollEffect` (para na última música) e recebe só `queue`/`queueIndex`/`queueSize`, nunca o `PlaybackState` inteiro (que muda a cada 0,5 s tocando e, recompondo a fila no meio da rolagem, abria um vão no fim) e, como o player, não passa do topo quando a mola da abertura sobra (`translationY` nunca negativo). Depois de soltar uma música arrastada, a fila segura a ordem nova (`pendingOrder`) por 1 s, ignorando qualquer fila com outra ordem: o player confirma a ordem nova, mas às vezes ainda chega um aviso atrasado com a antiga **depois** da confirmação, e a música piscava no lugar de antes.
- **Adicionar à fila:** `PlaybackController.playNext(track)` põe a música logo depois da atual (com o aleatório ligado, também na ordem original: `ShuffleState.insertAfter`, testado). Nos menus é `playNextAction` (um por feature: library, profile, wellbeing), tipo `BoomMenuKind.PlayNext`.
- **Playlists e álbuns:** capa de playlist com 4 ou mais álbuns diferentes é o mosaico 2 × 2, uma capa por álbum, **sem nunca repetir** (`mosaicCovers`, testado; `BoomMosaicArtwork`, core/designsystem); com menos de 4 álbuns, a capa da primeira música. As formas de 2 (metades) e 3 ("Y") foram recusadas pelo rilclesaraiva na 0.51.1: não volte a criá-las. A página de playlist/álbum/gênero (`CollectionDetailScreen`) não tem barra: capa grande de ponta a ponta esmaecendo no fundo, nome centralizado em cima, botões com tocar redondo grande à direita e o menu da playlist na linha de botões. Diferente da página do artista de propósito.
- **Buscas presas no topo** (Início e Artistas): `BoomStickyHeader` (core/designsystem) tem a faixa das notificações embutida, sólida só quando preso de fato (`rememberStickyHeaderStuck`: primeiro item visível ≥ cabeçalho; nada de escurecer antes, chegando perto, que cortava o que passava por baixo); o item de antes usa `tuckUnderStickyHeader()` para a faixa transparente ficar por cima do fim dele (sem vão grande entre o conteúdo e a busca).
- **Tocar de uma lista:** `play(tracks, startIndex)` monta a fila com a escolhida no topo, as seguintes e depois as anteriores (`queueStartingAt`, testado).
- **Aleatório é nosso, não do ExoPlayer.** O serviço usa `ShuffleOrder.UnshuffledShuffleOrder`, então a fila do player é sempre a ordem real. `ShuffleState` (classe pura, testada) embaralha com Fisher-Yates, guarda a ordem original e restaura ao desligar. `shuffleModeEnabled` só guarda se o aleatório está ligado. Toda nova forma de tocar aleatório passa por `PlaybackController.playShuffled` ou `toggleShuffle`.
- **"Mais ouvidas":** quem decide se uma reprodução conta é `PlayCountTracker` (puro, testado) dentro do `PlaybackService`: conta se o usuário **escolheu** a música (lista ou fila, marcada por `ChosenSongSignal` no controller) ou se ela tocou **na ordem normal**; **não** conta se entrou sozinha pelo aleatório; exige **30 s ouvidos de verdade** (80% em músicas menores que 30 s); uma vez por reprodução. O serviço avisa por `PlaybackHooks.onPlayCounted`, que o `BoomApplication` liga às estatísticas (`data/wellbeing`).
- **Backup** (Ajustes → Backup, `BackupScreen`/`BackupEngine`, feature/settings): um .zip escolhido pela pessoa (SAF, sem permissão) com as pastas de `filesDir` da pessoa (`USER_DIRS`: favorites, playlists, profile, stats), os SharedPreferences (menos `update_prompt` e os de bibliotecas) e o DataStore, mais um `manifest.json` (app, `format`, versão) com a descrição de cada música citada. Os endereços `content://media/…/ID` mudam de um celular para outro: ao restaurar, `matchBackupTracks` (puro, testado) acha cada música por endereço+arquivo, pasta+arquivo, arquivo+duração ou título+artista(+álbum)+duração, e `remapMediaUris` troca os endereços nos JSON (com ou sem a "/" escapada). Restaurar substitui tudo e reinicia o app (`restartApp`). **Arquivo novo de dados da pessoa tem que entrar em `USER_DIRS`** (ou ficar em SharedPreferences/DataStore), senão fica fora do backup. Entradas do zip só são aceitas com nomes conhecidos e sem "..".
- **Opções de reprodução extras** (`PlaybackPrefs`): ReplayGain (`replayGainDb`/`replayGainVolume`, puros e testados: lê REPLAYGAIN_TRACK_GAIN de ID3/Vorbis/MP4 e R128_TRACK_GAIN do Opus nas faixas do player, `onTracksChanged`, e só baixa o volume, via `VolumeMixer.replayGain`); voltar a tocar quando o fone reconecta (pausa por `AUDIO_BECOMING_NOISY` + `AudioDeviceCallback`, sem permissão de Bluetooth, até 30 min); lembrar o aleatório (`SharedShuffle`, o mesmo `ShuffleState` do controller e do serviço; o snapshot guarda o aleatório e a ordem original depois de `#original`, e arquivos antigos continuam lendo); letra da internet primeiro (`lyricsOnlineFirst`: LRCLIB antes e a do arquivo se não achar).
- **Lembrar onde parou:** o `PlaybackService` guarda a fila, a música e o ponto (`PlaybackSnapshotStore`, arquivo em `filesDir/player`) a cada mudança e a cada ~5 s tocando, e restaura pausado ao abrir. Fila vazia (música encerrada pelo mini player) apaga o arquivo: o app volta limpo. O aleatório só volta ligado com "Lembrar o aleatório"; sem a opção, a fila volta na ordem em que estava.
- **Histórico:** regra diferente das "mais ouvidas": entra **toda** música ouvida 30 s (inclusive as do aleatório), uma vez por reprodução (`PlayCountTracker.checkListened` → `PlaybackHooks.onListened` → `HistoryData`).
- **Navegação sem toque repetido:** toda navegação passa por `navigateOnce` / `popBackStackOnce` (core/common). `navigateOnce` só ignora o toque enquanto a tela que ela mesma acabou de abrir ainda está entrando (não RESUMED); depois de voltar, a tela de baixo aceita toque na hora, sem esperar a animação de saída. `popBackStackOnce` age só com a tela atual RESUMED. Nunca chame `navigate` ou `popBackStack` direto (só a troca de abas no `:app`). O "voltar" do sistema também espera: um `BackHandler` no `:app`, depois do `NavHost`, segura o voltar enquanto a tela atual não está RESUMED (dois voltar seguidos deixavam duas telas sobrepostas).
- **Lançamentos lembram as escolhas:** modo, filtro e janela ficam em `ReleasesChoicesRepository` (data/releases, SharedPreferences) e voltam ao abrir.
- **Abas:** Início (músicas) · Biblioteca (gêneros, artistas, playlists, álbuns) · Perfil (seu perfil, só seu). Lançamentos e Ajustes não são abas: ficam no canto superior direito das abas, nesta ordem (sino de Lançamentos, depois Ajustes), com `BoomTopActions`; no Perfil fica só Ajustes (sem o sino). Lançamentos abre como tela de dentro (com voltar). O histórico completo fica dentro do Perfil ("Histórico" → ver tudo); não há botão de histórico no topo. Não existe aba Amigos. Tocar na aba já aberta sobe a lista ao topo (`LocalTabReselect` + `ScrollToTopOnReselect` em toda lista de aba); numa tela de dentro da aba, volta ao começo dela. A subida é `scrollToTopSmoothly`: pula sem animação para uma tela abaixo do topo e anima esses pixels de uma vez (nunca `animateScrollToItem` com o alvo fora da tela, que anda em etapas e trava).
- **Tela larga (tablet, celular deitado):** usa o mesmo layout do celular em pé (barra de abas embaixo, player em coluna). O layout próprio (barra lateral, painel do artista tocando, player com a capa ao lado) saiu em 30/10/2026 por decisão do rilclesaraiva. Abrir o artista já aberto não empilha outra página (`openArtist` no `:app`).
- **Favoritos:** `FavoritesRepository` (data/library, `filesDir/favorites/favorites.json`, a favoritada por último primeiro). Coração no player cheio e "Favoritar" nos menus das músicas (`favoriteAction` em cada feature); a lista é a rota `collections/favorites` (`navigateToFavorites`), primeira linha da pílula Playlists e botão da barra lateral.
- **Barra de abas só nas abas:** qualquer tela de dentro (artista, álbum, playlist, gênero, histórico, lançamentos, editor, ajustes) fica sem a barra de baixo. Ajustes (e Bem-estar) e o editor de tags também escondem o mini player. Só existe **um** editor de tags na pilha (`navigateToTagEditor` troca o anterior).
- **Biblioteca:** toda leitura de músicas passa por `LibraryRepository.getTracks()`, que já aplica o filtro de Ajustes → Biblioteca (`LibraryFilter`: pastas escolhidas e duração mínima). Ela se atualiza sozinha (observador do MediaStore → `version`); telas que listam músicas recarregam quando `version` muda. Nada de pedir permissão de pasta (SAF): as pastas vêm do próprio MediaStore de áudio.
- **Blocos com capa e texto embaixo:** o toque usa `shapes.medium` com folga embaixo (e o texto com 4 dp de recuo), senão o canto arredondado corta as letras.
- **Barra de cima:** some ao rolar para baixo e volta ao subir (`enterAlwaysScrollBehavior` no `BoomScreenScaffold`; telas com `largeTitle` continuam encolhendo). Rolar por código não passa pela barra; `ScrollToTopOnReselect` zera `LocalTopBarState.contentOffset` e traz a barra de volta (`heightOffset` → 0) quando a lista chega ao topo, senão ela ficaria escondida ou com a cor de "rolado". Recolhendo, a barra vai ficando transparente (`collapsedFraction`): recolhida, a faixa das notificações mostra a página. - **Visualizador sobre a capa:** liga/desliga no menu ⋮ do player (`BoomMenuKind.Visualizer`, `PlaybackPrefs.visualizer`); tipo em Ajustes → Aparência → Visualizador (`VisualizerStyle`: barras, graves à esquerda, ou onda). O som vem da saída do próprio player: `BoomAudioSink.handleBuffer` passa o PCM ao `AudioVisualizer` (core/player), que analisa pedaços de 1024 amostras (`visualizerBands`/`waveformPoints`, puros e testados, 24 barras de 40 Hz a 16 kHz) e guarda cada um com o tempo da música; a tela (`CoverVisualizer`, feature/nowplaying) mostra o do ponto que está tocando (`getCurrentPositionUs`), suavizado (`smoothVisualizer`). Só analisa com um visualizador na tela e o app aberto (`attach`/`detach` em `LifecycleStartEffect`); pausado, desce até zerar e para de redesenhar. **Nunca** usar a API `Visualizer` do Android (exige `RECORD_AUDIO`). Nada de botão na capa (pedido do rilclesaraiva). O escurecido atrás dele fica mais forte quando a parte de baixo da capa tem pouco contraste com a cor dele (`visualizerScrimAlpha`, puro e testado, de 0,55 a 0,88; amostras em `sampleBottom`). Nos Ajustes cada tipo tem um desenho (`BoomIcons.GraphicEq` e `BoomIcons.Waveform`).
- **Vários artistas:** abrir o artista de uma música com mais de um (`splitArtistNames`) abre `BoomArtistChooserSheet` (core/designsystem): cada um com a foto num círculo (`DeezerRepository.artistPicture`, data/deezer; a inicial sem foto) e o nome inteiro por último; com um só, abre direto. Quem decide é `rememberArtistOpener` (feature/nowplaying, público): o player usa o dele, e o `:app` embrulha o `openArtist` das outras telas (`openSongArtist`). O player chama o `openArtist` cru do `:app` (senão escolher o nome inteiro abriria o painel de novo).
- **Capa nas tags automáticas:** com as tags já certas (`AlreadyCorrect`), o cartão mostra a capa da pessoa ao lado da encontrada e "Usar esta capa" (`useFoundCover`, troca só a capa, com Desfazer). O app não decide sozinho qual capa é a certa.
- A capa do player cheio não tem cor de toque (`indication = null`): segurar não pinta nada por cima.
- Ícones de player (pausa, próxima, aleatório…) são desenhados em `BoomIcons` a partir dos caminhos dos Material Icons. Não adicione o pacote `material-icons-extended` (pesa vários MB).

## Perfil (sem social)

- **O app não tem nada de social** (decisão do rilclesaraiva, 0.33.0): sem amigos, sem "ouvindo agora", sem recomendações, sem reações, sem redes no perfil, sem servidor. Música local e social não combinam aqui. **Não volte a criar nada disso.**
- O perfil é **só da pessoa e só no aparelho**, como deixar o próprio sistema bonito para si mesmo: nome, descrição (até 160 letras), cor, foto e capa. Módulos: `data/profile` (`ProfileRepository` → `LocalProfileRepository`, arquivo `filesDir/profile/profile.json` e as imagens `filesDir/profile/{avatar,banner}`) e `feature/profile` (aba Perfil: `MY_PROFILE_ROUTE` = `profile`).
- Imagens vêm do Photo Picker (sem permissão), recortadas e reduzidas no aparelho (`prepareProfileImage`: foto 512×512, capa 1080×405, WebP); GIF de até 8 MB vai como está, GIF maior ou vídeo de até 15 s vira GIF menor (`animatedProfileGif` + `GifEncoder`, 6 a 15 quadros por segundo; abaixo disso fica travado). A versão da imagem é a hora em que foi trocada (a tela relê quando muda).
- "Editar perfil" (lápis, ou tocar na foto, na capa ou no nome) só grava ao tocar em Salvar; fecha puxando para baixo **só pela faixa de cima** (`dragOnlyFromTop`: o conteúdo fica com a rolagem que sobra, senão rolar até o topo e continuar puxando fechava sem querer), pelo voltar ou tocando fora (sem X; pedido do rilclesaraiva na 0.40.1/0.40.2). A cor tinge o perfil (`Modifier.profileBackground`): degradê do topo para baixo (padrão) ou sólida no perfil inteiro (`MyProfile.solidColor`, "solid" no JSON; arquivos antigos sem ela ficam no degradê). Sólida, a página é a própria cor, opaca (#000000 é preto puro em qualquer tema), e o `BoomProfileSurface` (core/designsystem) troca as superfícies do tema por tons dela (`onSolidColor`: textos claros sobre cor escura e escuros sobre clara, cartões levemente mais claros/escuros).
- Estatísticas calculadas no aparelho (`ProfileStats.kt`, testado): números do mês, mais ouvidas, tempo por dia, horários de pico, seus artistas e histórico. Foto de "Seus artistas": Deezer pelo id se segue, senão pelo nome (`artistPicture`, como a página do artista), e só sem isso a capa de uma música dele. O mesmo vale para os artistas do Início e da Biblioteca → Artistas (`rememberArtistPhoto`, feature/library, com memória `ArtistPhotoMemory` para não piscar ao rolar; `artistPhoto` nos dois ViewModels).
- **Migração da 0.32:** na primeira abertura, `LocalProfileRepository` traz nome, descrição, cor, foto e capa de `filesDir/social` e apaga essa pasta inteira (o @, o segredo e o resto do social). O servidor (`boomlistener-social` na Cloudflare) foi apagado pelo rilclesaraiva em 20/10/2026 e o código dele saiu do repositório. O único Worker que resta é o proxy do Last.fm.

## Proxy do Last.fm

- `proxy/worker.js` (Cloudflare Worker `boomlistener-lastfm`, publicado pelo rilclesaraiva pelo painel). Só aceita métodos públicos de leitura e acrescenta a chave. Endereço no app: `PROXY_URL` em `data/lastfm/ProxyLastfmRepository.kt`.
- A chave e o segredo do Last.fm ficam **só** nos Secrets do Worker (`LASTFM_API_KEY`, `LASTFM_SHARED_SECRET`). Nunca escreva os valores em arquivo, commit, log ou mensagem.
- Esta sessão não tem acesso à Cloudflare: qualquer mudança no `worker.js` precisa ser colada de novo no painel pelo usuário.

## Build: AGP 9

- **AGP 9.4 + Gradle 9.6 + Kotlin 2.4**, `compileSdk 37`, `targetSdk 36`, `minSdk 26`, Java 17.
- O AGP 9 tem **Kotlin embutido**: nunca aplique `org.jetbrains.kotlin.android` num módulo (ele só é declarado na raiz para fixar a versão do Kotlin). `kapt` não funciona; use KSP.
- Plugins de convenção usam a DSL nova: `CommonExtension` **sem** parâmetros de tipo, `ApplicationExtension` e `LibraryExtension`. Nada de `BaseExtension` ou `applicationVariants`.
- Todo módulo é uma biblioteca Android (inclusive `core/model`), para não misturar alvos de JVM. `core/model` continua sem nenhum `import android.*`, por regra.
- **R8 ligado no release** (0.52.4: `isMinifyEnabled` + `isShrinkResources`, regras em `app/proguard-rules.pro`). APK caía de 19,6 MB sem ele. Com `-dontobfuscate`: encolhe e otimiza, mas os nomes ficam legíveis nos erros (o `mapping.txt` da Action não baixa daqui). O TagLib (JNI) tem `-keep`. Código novo que use reflexão, busca de classe pelo nome ou recurso por `getIdentifier` **precisa** de regra nesse arquivo. Se algo só quebrar no release, a suspeita é o R8.
